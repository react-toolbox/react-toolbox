# Material Design 1 audit

The [16 October component readiness review](component-review.md) records the later audit and implementation outcome across every public family. The pass unifies modal ownership and family theming, corrects interaction and composition defects, reduces shared CSS, and adds range sliders/calendars, scheduling constraints, gesture sheets and an editable themed distribution. Its recorded verification supersedes the earlier results below; statements about missing capabilities describe the revisions under review.

This document preserves historical audit findings and validation results. Test counts and CSS/React 16 comparison results belong to the recorded revisions. The completed migration's archived renderers, correction ledgers, and rebuild/comparison tooling were subsequently retired and remain available in Git history. Maintained regression tests check current behavior, Material 1 geometry and motion, themes, accessibility, and installed-source integration directly.

## Documentation interface — 15 October 2026

The documentation shell is reviewed against M1 [typography](https://m1.material.io/style/typography.html), [color](https://m1.material.io/style/color.html), [keylines](https://m1.material.io/layout/metrics-keylines.html), [navigation drawers](https://m1.material.io/patterns/navigation-drawer.html), [data tables](https://m1.material.io/components/data-tables.html), and [accessibility](https://m1.material.io/usability/accessibility.html).

- Roboto uses the M1 display, title, body, and caption scale. App-bar titles are 20px medium; section titles are 20px medium, with 16px subheadings. Primary prose uses 87% black and supporting text 54%. Paragraphs, lists, examples, and tables share the article width within the bounded documentation shell.
- Content follows the 8px layout and 4px type grids, with 16px phone and 24px tablet insets. Desktop content uses a larger 48px gutter. The app bar follows 56px phone portrait, 48px short landscape, and 64px desktop/tablet heights.
- Permanent navigation stays on the content plane below the app bar, scrolls independently, and remains pinned when the footer enters the viewport or article height changes. Temporary mobile navigation retains its modal focus handling. Standalone navigation and footer links have 48px targets.
- The reference uses Material table spacing, 12px column headings, 13px data, and rows at least 48px high. Wide tables and source examples scroll locally and remain keyboard accessible. Monospace code, syntax colors, copy controls, and the article contents list are documentation conventions rather than separate M1 component specifications.
- API pages show selected behavior props and source-derived defaults. Full TypeScript declarations and compatibility slot listings remain in the source instead of being repeated in the UI. Theming leads with global CSS variables, `className` on composed parts, and editable source; existing slot-map APIs remain compatible.

`apps/docs/tests/browser/documentation.spec.js` checks all 27 component pages and four guide/index pages at phone and desktop widths with axe, verifies key dimensions and colors, and exercises navigation, copy controls, preview/code tabs, modal focus, and the sidebar/footer regression in Chromium and WebKit. Automated checks supplement the visual review; they do not certify every possible user theme or content combination.

## Component quality and primitive review — 15 October 2026

This follow-up reviewed all **27 public registry families**, their documented consumption examples, and their shared behavior. The target remained M1. shadcn was the comparison for composition, accessible interaction, and source ownership, not a replacement visual specification. The earlier measurement ledger and immutable React 16/CSS reference were used during this pass.

The comparison used shadcn's [Radix component catalog](https://ui.shadcn.com/docs/components), its maintained [component source](https://github.com/shadcn-ui/ui/tree/main/apps/v4/registry/new-york-v4/ui), [Radix Avatar](https://www.radix-ui.com/primitives/docs/components/avatar), [Radix Dialog](https://www.radix-ui.com/primitives/docs/components/dialog), and the [roving-focus implementation](https://github.com/radix-ui/primitives/tree/main/packages/react/roving-focus). These upstream sources evolve; this records the decision made on the audit date, not a promise that every future shadcn implementation has the same internals.

### Adoption boundary and evidence

The installed behavioral dependencies are Radix Avatar 1.3.1, Radix Roving Focus 1.2.1, and aria-hidden 1.2.6. The registry derives and installs each dependency from source imports; they are not bundled into every family. Native controls share a small form-reset foundation. The RadioGroup context replaces direct-child cloning so composition works through intermediate elements.

A wholesale Dialog/Select/Menu migration is not presented as completed. Their existing API includes externally managed openers, value-first callbacks, static content, custom templates, exit retention, and scoped portal themes. The changes above fix identified defects while keeping those contracts; future migrations need to demonstrate a simpler implementation under the same tests. Conversely, choosing a native input or table is already consistent with shadcn's approach and does not require a Radix dependency to be accessible.

Regression evidence is grouped by behavior in `tests/native-forms.test.tsx`, `tests/autocomplete.test.tsx`, `tests/overlay-accessibility.test.tsx`, and the other component and browser suites, alongside state, keyboard, Material geometry, hydration, reduced-motion, and registry-consumer checks. The migration also compared original declarations with explicit M1/accessibility corrections; that verifier has been retired. This is a component review with bounded automated evidence, not a completed VoiceOver/NVDA audit or certification of every consumer composition. The manual release checks in [accessibility.md](accessibility.md) remain explicit.

Validation completed for this change: `pnpm check` (production builds, lint, types, unit tests, styles, registry closures, API and release checks); 139 unit tests; 138 Chromium and 138 WebKit browser tests; and real shadcn CLI installation from the production docs registry into clean Next.js and Vite consumers, including coexistence with an official shadcn Button. The final Chromium suite ran with two workers after an intermittent 22-pixel slider-halo compositor difference under concurrent browser workloads; the isolated case and complete rerun passed without loosening pixel equality. The new mixed checkbox state and corrected chip-container semantics had explicit reference adapters in the migration test harness; archived CSS/runtime fixtures were unchanged during this verification.

### What this establishes

### Integration corrections discovered while implementing

- The earlier Tooltip decorator fixes remain: slotted Button/links retain a single child and refs, pending hints cancel on activation, and an exiting hint cannot swallow a menu's Escape.
- Base UI's Combobox.Label labels a trigger, not an external search input. AutocompleteLabel uses a native label associated with the root's stable input id; consumers can supply `htmlFor` with a custom input id.
- State-specific animation selectors outranked the initial reduced-motion utility. Compound parts now explicitly disable those animations when reduced motion is requested.
- A clean Next.js source installation exposed missing animation definitions: separately compiled CSS discarded unused `@theme` keyframes, so closing surfaces could wait indefinitely for an animation that never ran. Registry items now also register the keyframes referenced by each family's actual TypeScript import graph through shadcn's [registry CSS API](https://ui.shadcn.com/docs/registry/registry-item-json#css). Minimal Button installations still exclude unrelated checkbox/progress animations. Definitions remain derived from their maintained CSS sources.
- M1 presentation is shared through CSS tokens and static Tailwind classes: dialog spacing/elevation, drawer widths, popup geometry, the tab indicator, touch targets, typography, and motion. Scoped theme variables are applied to the actual portaled surface so primitive presence lifecycles remain intact.

### What belongs in configuration versus components

All **six composition gap groups** required component/API changes; **zero** could be solved by Tailwind configuration alone. Child discovery, stable selection identity, focus/dismissal, native form integration, portals and provider coordination require behavior and structure. Presentation changes use the existing M1 tokens and class-name composition. The animation installation correction belongs in the registry build; reduced-motion precedence belongs in component styling. No new theming API or host-wide Tailwind configuration is needed.

Date ranges, multiple slider thumbs, bottom sheets, a dedicated field family, virtualization recipes and a snackbar queue remain additional capabilities, not claims of this pass. Base UI's collection/filtering hooks are available through its root props, but large virtualized lists have not been validated here. A snackbar queue should preserve M1's single visible message rather than stack concurrent toasts.

## Compatibility decisions

- Continuous sliders now follow the M1 state illustration: 12px at rest, 14px on hover, and 18px when pressed, with the existing larger interaction container. The hollow minimum rail gap follows the pressed thumb size.
- Original primary/accent branding, public component props, theme slots, and value-first callbacks remain the default contract. The audit does not recolor every selection control to a different accent or replace the public API with another component library.
- Existing motion curves and keyframes remain except where a documented correction is explicit. Calendar month transitions remain 350ms, clock view transitions 500ms, and existing ripple timings are retained; ripple sizing now accounts for the taller dimension of a target. Tooltip timing changes are listed above. M1's timing guidance is contextual, so preserving an existing duration is not a claim that all transitions must use one universal value. [Duration and easing](https://m1.material.io/motion/duration-easing.html).
- Runtime modernization uses typed function components and hooks, with DOM refs or explicit typed imperative handles. Component injection factories, styling wrappers, and runtime PropTypes are removed. Generated IDs and ARIA attributes change markup where necessary. Native disabled behavior and picker activation corrections are intentional behavioral differences.
- CSS custom properties and theme slots remain configurable. Scoped overrides only recompute dependent tokens and follow portaled content. The clock face has its own background token; a divider correction should not recolor a decorative surface accidentally.

## Validation and limits

Maintained focused tests live in `packages/react-toolbox/tests/m1-*.test.jsx` and `packages/react-toolbox/tests/browser/m1-*.spec.js`. They complement runtime, hydration, type, theming, and registry-consumer checks. Checks include real Chromium/WebKit geometry, control state ink, actual button hit areas, modal interactions, slider press/release, and progress animation samples. Browser fixtures that load current CSS directly isolate styling; gallery tests exercise the React output and integration. Run the current checks with `pnpm check`, `pnpm docs:build`, and `pnpm test:browser`; select WebKit with `TOOLBOX_BROWSER=webkit`. These commands no longer run historical CSS or React 16 comparisons.

Coverage is bounded. Passing these tests does not establish every font rasterizer, browser, screen reader, touch device, theme combination, or application flow as conformant. In particular:

- No automatic dark-theme palette, landscape picker variant, expanded contact-chip detail view, or automatic locale-based 12/24-hour detection was added. Existing props and explicit theme overrides remain available.
- General `--color-text` and secondary palette aliases remain for compatibility. Opaque legacy text greys do not reproduce alpha compositing on every colored surface; the specifically corrected state tokens use alpha ink. [M1 color guidance](https://m1.material.io/style/color.html).
- Dropdown now participates in native required-field validation through a select that mirrors its displayed value; application-specific validation still belongs to the consumer.
- Applications supply meaningful labels, modal names, actions, localized error wording/icons, and layout spacing. The library does not prepend an English error prefix, allocate every surrounding touch target, coordinate consecutive snackbars/FAB movement, or decide when an overlong menu should become a dialog.
- Optional platform/density variants and a full assistive-technology, RTL, contrast, and reduced-motion audit remain separate work. Additional variants should be evaluated against their own M1 evidence rather than inferred from Material 3 or from the legacy implementation alone.
